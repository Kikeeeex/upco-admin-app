# Decisiones y dependencias

1. **Stack local:** Next.js 16, React 19, TypeScript, Tailwind 4, Supabase JS/SSR y PostgreSQL. Versiones resueltas desde npm el 28/10/2026 y fijadas en `package-lock.json`. Se revisaron las guías de autenticación, Cache Components y Proxy incluidas en `node_modules/next/dist/docs/`. Las páginas oficiales de Supabase y Microsoft devolvieron HTTP 403 por la política de salida del entorno; el flujo OAuth debe contrastarse con ellas antes de conectarlo a Entra corporativo.
2. **Acceso cerrado:** sin configuración de Supabase/tenant, no hay sesión ni datos. No se implementa cuenta local de prueba ni se confía en correo, dominio o metadatos editables.
3. **Tenant e identidad:** el tenant esperado se configura en servidor. La identidad Azure que Supabase entregó en la prueba real contiene `custom_claims.tid`, `sub`, `provider_id` e `iss`; no contiene `oid`. La autorización compara el tenant y el sujeto estable `sub` con una membresía activa, exige que `sub = provider_id` y valida el emisor de Microsoft para ese tenant. El campo `entra_object_id` queda opcional como dato de auditoría, sin participar en el permiso. El correo o dominio no conceden acceso.
4. **Recursos externos:** UPCO debe aprobar proveedor/región, clasificación de datos, retención, respaldo, dominio, proyecto Supabase de desarrollo, registro Entra, consentimiento OAuth, callback de Entra `https://<supabase-project>.supabase.co/auth/v1/callback`, redirección de la app `<origen>/auth/callback` y usuario administrador inicial. El proyecto Supabase y el tenant se enlazan mediante `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY` y `ENTRA_TENANT_ID`. La política de red debe permitir el host exacto de `SUPABASE_URL` una vez conocido. No hay valores reales en este repositorio.
5. **Pruebas:** usar solo datos sintéticos. Las pruebas locales de lógica y SQL no sustituyen una prueba de OAuth con cuenta corporativa autorizada ni una revisión de seguridad previa a producción.
6. **Identidad:** `src/features/auth/authorize.ts` lee `custom_claims.tid`, `sub`, `provider_id` e `iss` desde `user.identities[].identity_data` del proveedor Azure y rechaza cualquier dato faltante o incoherente. La forma de estos campos se comprobó en la identidad de Supabase creada por el primer login corporativo. El proxy renueva cookies; rutas y acciones vuelven a comprobar autorización.
7. **Migraciones remotas del 28/10/2026:** se aplicaron `20261028000000_core.sql` y `20261028000001_restrict_table_privileges.sql` al proyecto de desarrollo mediante la API de administración de Supabase, cada una dentro de una transacción. Se registraron ambas versiones en `supabase_migrations.schema_migrations` con el formato de la CLI (columnas `version`, `statements`, `name`; `statements` quedó NULL porque se ejecutaron por API). La primera migración creó ocho tablas y nueve políticas; la segunda retiró privilegios amplios que este proyecto concede por defecto a `anon` y `authenticated`. La suite SQL remota pasó con datos sintéticos en una transacción terminada en `ROLLBACK`. No quedaron organizaciones, membresías, actividades ni usuarios sintéticos. Versiones y SQL fuente permanecen en Git.
8. **OAuth pendiente:** el proveedor Azure está activo y redirige al tenant configurado con el callback de Supabase. No existen aún usuarios ni identidades Azure en este proyecto; el login completo y la provisión explícita de la primera membresía siguen sin verificar.
9. **URL de pruebas creada por el usuario:** `https://upco-admin-app.vercel.app/` sustituye a la dirección de staging prevista. En Supabase Auth, Site URL debe ser `https://upco-admin-app.vercel.app` y Redirect URLs debe incluir `https://upco-admin-app.vercel.app/auth/callback`. La URL del callback en Entra no cambia: apunta a Supabase Auth. El 28/10/2026 se verificó `/login` con HTTP 200, botón Microsoft habilitado, ruta privada sin sesión redirigida a login y el inicio de OAuth hacia el tenant configurado. El primer token de acceso a la API de administración de Supabase fue revocado por el usuario tras aplicar las migraciones iniciales; se creó otro temporal para provisionar la primera cuenta.
10. **Identidad real y tercera migración:** el 28/10/2026 el primer login corporativo llegó a `/acceso-denegado`. La inspección administrativa de `auth.identities` encontró una identidad Azure con `custom_claims.tid` y `sub` de 43 caracteres, sin `oid` ni `tenantid` en el nivel superior. La migración `20261028000002_azure_subject.sql` añadió `entra_subject` a perfiles y membresías, dejó `entra_object_id` como opcional y fue aplicada y registrada en el proyecto de desarrollo. Una prueba de permisos SQL con datos sintéticos pasó en la base remota con `ROLLBACK`. La identidad y el esquema se validaron antes de provisionar acceso.
11. **Administración inicial de pruebas:** el usuario confirmó la cuenta administradora. Se creó una organización de pruebas, un perfil y una sola membresía `admin` activa en una transacción; otra consulta confirmó que tenant y sujeto coinciden con `auth.identities` de Azure. Una prueba con el rol `authenticated` y ese usuario vio exactamente su organización y membresía, creó un registro sintético y su evento de auditoría, y se revirtió con `ROLLBACK`. Después quedaron cero registros de trabajo, eventos y contadores. El usuario confirmó que pudo abrir el panel en Vercel.
12. **Flujo real de actividades:** el usuario creó y editó una actividad sintética en «Mi trabajo» desde Vercel. Consultas administrativas verificaron su pertenencia a la organización y cuenta autorizadas, código generado, prioridad Alta, estado En progreso y dos eventos de auditoría (creación y actualización). No se probaron aún cierre, reapertura ni archivo desde el navegador. Tras esta comprobación, el token temporal de administración ya no es necesario y puede revocarse.
13. **Notas y archivo de Sprint 1:** se añadió `20261028000003_work_item_notes.sql` al historial de migraciones. Las notas son eventos `note` inmutables en `activity_log`: el usuario autenticado solo puede insertar texto de 1 a 2000 caracteres en una actividad propia, activa y de su organización; no puede falsificar `created`/`updated` ni modificar eventos anteriores. El trigger existente registra archivo/restauración y cierre/reapertura. SQL local y remoto pasó con rollback; falta validación de la interfaz en staging.
14. **Consulta completa del archivo e historial:** la revisión detectó que el límite de 50 actividades y 1000 eventos impedía recuperar registros antiguos. Se sustituyó por paginación independiente de actividades activas, archivo y eventos por ficha. Se usa la zona horaria del perfil para mostrar fechas; el autor se muestra con su nombre visible si es accesible y, en otro caso, con su identificador estable de usuario. Se ocultaron acciones de edición y archivo a usuarios distintos del creador; el servidor sigue comprobando la autoría y ahora impide que un formulario abierto antes del archivo modifique el registro. La suite SQL cubre el rechazo de notas sobre registros archivados y por otro miembro de la misma organización.
15. **Búsqueda y filtros BL-11:** `20261028000004_work_item_search.sql` añade una columna `search_text` generada con código y título, más índice trigram; la aplicación la consulta con `ILIKE`, escapa `%` y `_`, y rechaza `*` porque PostgREST lo interpreta como comodín. Los demás filtros usan columnas existentes y se aplican a la consulta bajo RLS antes de paginar. «Vencidas» usa el día en la zona del perfil y excluye actividades completadas o canceladas. La migración y la suite SQL con rollback pasaron en Supabase de desarrollo; se conservaron los datos previos.
16. **Prueba de nota y archivo en staging:** el usuario confirmó que al añadir una nota, archivar y restaurar la actividad de prueba, la nota y el historial permanecieron visibles. La base mostró una actividad activa, cinco eventos y una nota, coherentes con creación, edición, nota, archivo y restauración.
17. **Prueba de filtros y cierre en staging:** el usuario confirmó una búsqueda por título combinada con prioridad Alta y la exclusión al cambiar a Baja. También completó y reabrió la actividad, con fecha de cierre visible solo mientras estaba completada e historial conservado. La base confirmó el estado final `in_progress`, `closed_at` vacío, siete eventos y una nota. El filtro por sede pasó en SQL; faltan sedes de prueba para usarlo desde la interfaz.
18. **Identidad visual UPCO:** el manual y tres PNG entregados por el usuario fijan verde `#0B4B32`, oscuro `#041914`, gris `#EDEDED`, Satoshi para títulos y Helvetica Neue para texto. Se colocaron las variantes clara y verde sobre los fondos permitidos, conservando proporción y espacio de reserva. Satoshi se convirtió de los OTF adjuntos a WOFF2 y se sirve desde la app con atribución a Indian Type Foundry. El repositorio es público; el usuario optó por no publicar los archivos de Helvetica Neue mientras no haya certeza de que la licencia lo permite. La CSS utiliza Helvetica Neue si está instalada y alternativas del sistema en los demás equipos.
19. **Límite de sesión:** a petición del usuario, el acceso de UPCO Admin vence tras 30 minutos sin interacción o 8 horas desde el callback OAuth. Dos cookies HttpOnly propias registran la actividad y el inicio de cada sesión, sin depender de `last_sign_in_at` global de Supabase. El proxy y el contexto de autorización comprueban ambos plazos; la vista abierta envía actividad mediante POST y cierra al vencer. GET y precargas no renuevan la actividad. Al desplegar la política, los usuarios con sesiones antiguas deberán ingresar de nuevo para recibir los marcadores. La sesión SSO de Microsoft tiene su propia duración.
20. **Gestiones administrativas BL-13:** se sigue el modelo 1:1 de la especificación: `work_items` mantiene asunto, código ADM y fecha de compromiso como `due_date`; `admin_details` contiene tipo, contraparte, referencias, estado documental y enlace. Los tipos y contrapartes son texto libre porque no hay catálogo definido. Una función PostgreSQL `SECURITY INVOKER` crea ambas filas en una transacción y aplica RLS; un trigger de restricción diferido impide cualquier ADM sin detalle y otro audita cambios documentales. Las gestiones ADM creadas con el formulario general anterior reciben detalle «Sin registrar» y estado documental pendiente para que sigan visibles. El nuevo formulario general dirige las gestiones administrativas a su sección. Dos migraciones del 29/10 se aplicaron y registraron en Supabase de desarrollo antes de publicar la interfaz.
21. **Compromisos administrativos BL-14:** un compromiso principal sigue usando `work_items.due_date`; los contactos sucesivos usan filas separadas de `follow_ups`, conforme al modelo lógico de la especificación. En BL-14 solo se admiten vínculos a ADM; BL-23 ampliará la agenda a otras áreas. Un seguimiento realizado conserva su resultado y no se reabre; reprogramar uno pendiente deja auditoría sin alterar la fecha principal.
22. **Sedes iniciales de pruebas:** el usuario confirmó Maracaibo y El Tigre como sedes de UPCO y delegó los códigos. En la organización de pruebas se configuraron `MAR` / Maracaibo y `TIG` / El Tigre; sus IDs se generan en Supabase y no se fijan en el código fuente.
23. **Proveedores BL-15:** el catálogo `vendors` pertenece a la organización y usa UUID como referencia para futuras solicitudes/cotizaciones. Nombre y área son obligatorios para las nuevas altas; contacto, correo, teléfono y observaciones pueden completarse después. El nombre es único dentro de la organización al ignorar mayúsculas y espacios repetidos. Se conserva el creador para restringir ediciones y no se permite borrado ordinario. La selección desde una solicitud se implementará en BL-16.
24. **Áreas y eliminación de proveedores:** el usuario definió SIAHO, Productos y Servicios, Operaciones, Administración, Finanzas y TI como áreas asociadas del proveedor. Son distintas del área de una actividad. Las filas previas quedan sin área hasta que el usuario las edite; las nuevas requieren una. «Eliminar» archiva con fecha del servidor y permite restaurar, de acuerdo con RN-12. El nombre sigue reservado mientras el proveedor esté archivado para evitar duplicados al restaurar.
25. **Retención de proveedores eliminados:** por solicitud explícita posterior del usuario, los proveedores archivados se muestran durante 30 días desde `archived_at` y luego se purgan automáticamente mediante un trabajo de Supabase que corre cada minuto. El creador puede eliminarlos permanentemente antes desde «Proveedores eliminados». Esta excepción específica reemplaza RN-12 para proveedores; el borrado definitivo no se ofrece para registros activos ni para otros módulos. Los nombres liberados pueden volver a usarse. Si futuras solicitudes o cotizaciones referencian proveedores, sus relaciones deberán permitir conservar el historial comercial sin impedir la purga.
26. **Directorio e importación:** los diez campos comerciales del Excel reemplazan la presentación antigua de proveedores. `associated_area` y `notes` se conservan internamente sin requerirse en nuevas altas; `sales_area` es independiente del área UPCO. El importador omite coincidencias por defecto y solo actualiza filas/campos seleccionados; los archivos originales no se guardan. El límite se fijó en 4 MB para dejar margen bajo el tope de 4,5 MB por petición de Vercel. Las dos migraciones se aplicaron antes de publicar la interfaz. El token inicial devolvió 401; tras actualizar y publicar el entorno cloud, la API respondió 201 y permitió aplicar y verificar las migraciones.

34. **Especificación fiscal/técnica de UPCO recibida (10/11/2026):** el archivo `ESPECIFICACION-ACTUAL-UPCO.md`, con corte de código al 09/11/2026, detalla fórmulas, redondeo, períodos, restricciones de exportación y estructura de archivos de la app fuente. 44. **Administración V2.7: confirmar lotes históricos de forma atómica (11/11/2026):** al confirmar se vuelve a analizar el archivo y se recalcula en servidor con el padrón y la configuración activa. Un único fallo revierte el lote; las observaciones exigen reconocimiento explícito. No se guardan los archivos ni se generan nuevos comprobantes. La configuración fiscal activa es obligatoria. Especificación: `docs/UPCO_Admin_Especificacion_MVP_v2_7.md`.

La asignación se audita en base de datos, el cambio es atómico y RLS aplica el mismo alcance que páginas, acciones y endpoints. El RPC de asignación solo se puede ejecutar con `service_role`; se verificó que `anon` y `authenticated` no tienen `EXECUTE`. La configuración fiscal permanece sin activar y no se modificaron documentos fiscales. Especificación: `docs/UPCO_Admin_Especificacion_MVP_v2_8.md`.
